## 一、项目现状一页总结

**方向**:把 TIGER 的"SID 逐位自回归 + beam search"改成"一次用户编码 + 并行位置打分 + 全目录矩阵排序",目标是保持质量的同时大幅降低推理延迟。

**当前主方法:π-SID ExpertScore v3**(详见《π-SID ExpertScore v3 方法说明.md》)

- 在线路径:FastTokenizer(字典查表)→ FastHistoryEncoder(无 attention,6 位位置周期 MLP)→ 3 个并行 SID 位置头 → rank-8 前缀条件后缀联合专家 + item alignment residual → 全目录打分
- 在线**没有** T5、beam search、flow matching、Euler 积分;teacher 只在训练期做表征/ logits 对齐
- 训练:CE(prefix+parallel)+ 目录采样 rank loss(2048 负例)+ InfoNCE align + hidden MSE/logit KL 蒸馏到冻结 MTP/T5

**方法演进链**(前三者是历史原型,文档已标注"已被取代",勿混用结果):

1. HiFlow-SID-OneStep(flow expert)— test NDCG@10=0.0223,质量差
2. π-SID-fast(快速编码器 + MLP chunk expert)— 纯速度原型
3. π-SID 分层 ChunkFlow(可蒸馏版)— test 0.0197,质量差
4. **ExpertScore v3(当前主方法)**— Beauty test NDCG@10=0.0260

**关键数字(Beauty,RecBoard 协议,full ranking)**

| 方法 | test NDCG@10 | test Hit@10 | 速度(相对 TIGER beam-50) |
|---|---:|---:|---:|
| TIGER(SDQ-T5-VAE,beam30) | **0.0411** | 0.0751 | 1× |
| MTP(并行头) | 0.0251 | 0.0461 | ~4.5× |
| SID-MLP-RecBoard(我们实现) | 0.0246 | 0.0457 | 3.46× |
| **ExpertScore v3** | **0.0260** | **0.0484** | **20.4×** |

- 速度口径:SID-MLP 规则(batch32/beam50/bf16/TF32 关/test 集/elapsed+吞吐),Beauty 上 TIGER 69.69s vs ExpertScore ~3.3s
- **未解决的质量问题**:所有并行方法 test NDCG@10 仍低于 TIGER 0.0411
- **完整质量/速度总表见 §二**

## 二、实验结果总表(质量 + 速度)

所有质量数均为 **RecBoard 协议**(Amazon 2014 5-core、leave-two-out、history≤20、full ranking、seen 掩码、seed 2025),**test 集**报告,valid 仅用于选 best(by NDCG@10)。Recall 与 HitRate 在 full ranking 下逐 cut 相等。速度统一按 **SID-MLP 规则**(batch32、beam50、原生 bf16、TF32 关、test 集全量、elapsed 总时间),空闲卡串行实测。

> **重要:本表所有方法共享同一个 SID tokenizer——SDQ-VAE。**
> TIGER 基线、MTP、HiFlow-SID、ChunkFlow、π-SID、ExpertScore v3、SID-MLP-RecBoard 全部加载同一个文件 `SDQ-403/logs/SDQ/Amazon2014{DS}_550_LOU/vae/sid_vocab.json`(你 SDQ-403 工作的 **Structure-Diffusion VAE** 3 位码、码本 256)。

> 质量差距全部来自"beam 自回归生成 vs 并行打分"的方法差异,与 tokenizer 无关——这是本项目的公平对照基础。

## 六、交接协议(Protocols)

### 1. 数据协议(RecBoard comparison contract)

- Amazon Review **2014 5-core**;Beauty/Sports/Toys
- 按用户时间序 **leave-two-out**;history 右对齐,**max 20**
- **full ranking** 评估,seen 物品掩码
- 指标:HitRate@1/5/10/20、NDCG@5/10/20、MRR@5/10/20(能配则配)
- beam=30(生成式方法)、seed=2025
- SID:SDQ-VAE **3 位码**(码本 256),`sid_vocab.json`;**所有方法(含 TIGER 基线、MTP、SID-MLP、ExpertScore)共用这一套 SDQ-VAE SID**,没有方法使用原版 TIGER 的 RQ-VAE 码

### 2. 速度协议(SID-MLP 规则)

- batch=**32**;TIGER:HF generate、KV cache、**beam=50**、无 Trie、max_new_tokens=4
- 原生 **bf16**、**TF32 关闭**;split=**test**
- 度量:**完整 test 集 elapsed 总时间 + 吞吐(用户/s)**,加速 = 总时间相除(QPS 相除等价)
- 参照脚本:`scripts/bench_sidmlp_rules_v2.py`;注意**只能空闲卡串行跑**,并行会互相抢卡使基线虚高

### 3. 环境与 GPU 守则

- Python:`/data/fszhang/anaconda/envs/myenv_t5/bin/python`(torch 2.7.1 / freerec 0.9.7 / transformers 5.17)
- 先 `nvidia-smi` 再挑卡;GPU 0/1 常被他人任务占满(100%),GPU 3 通常空闲;测速务必用**空闲卡**
- 后台训练统一:`setsid bash -c 'CUDA_VISIBLE_DEVICES=N ... > logs/x.log 2>&1' < /dev/null & disown`(直接 nohup 会随会话被 kill)
- 训练日志:freerec 写到 `./logs/{description}/{dataset}/{id}/log.txt`;自定义 tee 到 `logs/*.log`

### 4. 训练/评估规范

- **valid 调参选模型、test 报最终指标**;best 按 val NDCG@10
- epochs=200、eval_freq=5、**早停 patience 的单位是"评估次数"不是 epoch**(patience 15 × 5 = 75 epochs);想"best 后约 15 epoch 停"用 patience 3
- freerec `coach.fit()` 自动做:周期 valid → 早停 → 结尾 valid+test → eval_at_best(best 上再跑 valid+test)
- 全库打分模型 eval batch 可用 64;beam 基线 eval batch 写死 16 会极慢(历史 915s 问题)

### 5. 文档更新规范

- 数字更新改 `速度测试结果.md`(速度)与 `BASELINE_RESULTS.md`(质量);方法变更改《方法说明》+《最终Idea》
- 被取代的旧方案文档:头部加"状态:已被 XX 取代",**不要**删除历史数字,也不要转记为当前方法结果
- 所有测速原始数据落 `HiFlow-SID/results/*.json`,文档引用文件路径

## 七、已知问题与风险

1. **质量差距(最大风险)**:ExpertScore v3 test NDCG@10=0.0260 < TIGER 0.0411;若无法缩小,论文只能打"速度换质量"或需要更强的联合项

4. 速度数字有运行间波动(TIGER 69.7–80.0s、π-SID 2.7–3.3s),引用时用干净串行重测值;早期 29.2×、85× 等已被修正口径取代
5. SID-MLP 论文 8.74× 来自其 Amazon Reviews 2023 设置,我们同协议实现的 SID-MLP-RecBoard 只有 ~3.5×——写论文时不能直接引用 8.74× 作为我们的对标结果
6. Codex 配置:已修 `~/.codex/config.toml` 的 model 为 `gpt-6-astra`(原 `gpt-6-luna` 无效);账号目录里 sol/luna 只有 5.6 系列
7. 他人的 LARS/atomic_action 训练常驻 GPU 0/1/2,注意避让
